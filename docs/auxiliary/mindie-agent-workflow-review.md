# AI学伴辅助完成MindIE文本生成实验的流程评审

用户已于2026年10月22日确认本稿第8.2节六项决定。作为学习详情页AI学伴自动化场景的辅助材料和实施依据，第一版为明确标注的交互演示，不连接或执行真实服务器命令。原始评审内容保留，便于追溯。

## 1 核心结论与阅读方式

实验手册第2.2节共有 **7个主步骤**。建议顶部保持7步，每一步在对话中展开子任务，不把所有命令平铺到顶部。

**推荐方式：AI先解释目标和影响 → 用户选择或授权 → 右侧显示真实的用户回复气泡 → AI展示待执行命令并执行 → 用结果卡片展示回显和解释 → 验证通过后推进步骤。**

本稿按交互粒度拆为25个子任务。25不是手册原有的子步骤数量，而是便于评审的产品拆分。下文中：

- **原文**：来自《基于MindIE的文本生成推理实践》上机操作指导书第2.2节及其中截图。
- **建议**：为实现Agent交互补充的授权、校验、状态和分支规则，尚未实现。
- **待确认**：需要你确认的产品方案，或实施时需要用户选择的真实环境参数。

本稿不执行任何实验命令，不修改现有页面。手册中的版本、路径和回显是该实验的历史示例，不代表当前用户的实际环境，也不代表当前推荐版本。

### 1.2 本场景要解决的问题

原文需要学习者在网站、服务器主机、容器和配置文件之间切换。AI学伴的价值不是替用户做所有决定，而是减少重复输入，并把“当前在哪执行、改了什么、结果是否达标”呈现清楚。

| 已知依据 | 对交互的影响 |
|---|---|
| 用户要求参考安装助手的步骤、选项和回复气泡 | 对话需要承载选择、授权与执行证据，而不只是文字问答 |
| 手册包含主机命令与容器内命令 | 每条命令必须标明执行位置和目标环境 |
| 镜像获取涉及申请权限和密码 | 不能把所有步骤设计成一键无人值守 |
| 权重路径、设备、容器名需要按实际修改 | 需要可编辑的参数确认卡，不能照搬示例 |
| 部署成功后还需要发起推理请求 | 必须区分命令退出、容器运行、服务启动和推理成功 |

以上为输入材料和用户要求的归纳；尚无耗时、转化或完成率实测，不承诺具体节省比例。本轮不扩展竞品研究、商业预测或界面Demo。

## 2 自动操作与授权的边界

### 2.1 四种操作类型

| 类型 | 允许AI做什么 | 用户参与方式 | 例子 |
|---|---|---|---|
| A 直接整理 | 解析手册、解释命令、生成计划、准备参数草稿 | 无需服务器执行授权 | 说明Docker表头的含义 |
| B 授权后自动检查 | 在限定主机和范围内执行只读查询、解释结果 | 初次明确授权；范围未变时无需每条重问 | `npu-smi info`、`docker ps` |
| C 选择和授权后执行 | 下载、上传、创建容器、写配置、启动服务、发推理请求 | 先确定参数，再确认影响和本次操作 | `docker run`、修改config.json |
| D 用户亲自完成 | 登录、输入密码或验证码、申请访问权限、必要的管理员操作 | AI提供入口和说明，用户在安全界面操作 | 镜像权限申请、仓库凭据输入 |

“可自动”不等于“无需授权”。AI生成命令可以直接做，但在真实服务器执行必须受授权范围约束。用户说“帮我完成实验”不能直接视为允许特权容器、关闭HTTPS或覆盖文件。

### 2.2 建议的授权粒度

1. **只读检查可合并授权**：明确包含哪些命令、读取哪些目录、在哪台主机执行。比如第一步的NPU与Docker检查可一次授权两条命令。
2. **有副作用的操作按阶段授权**：权重下载/上传、镜像拉取、创建容器、写配置、启动服务分别确认，不要用最开始的一次“同意”覆盖全部步骤。
3. **授权绑定具体参数**：主机、路径、镜像、设备、容器名、网络方式、权限或配置差异变化时，旧授权失效，重新展示确认。
4. **敏感动作单独说明**：特权容器、主机网络、关闭HTTPS、覆盖已有文件、重启已有服务不能藏在“继续”里。
5. **拒绝不等于出错**：展示“未执行”，提供“我来操作”和“稍后继续”，不出现已授权气泡，也不推进完成状态。
6. **外部动作以证据为准**：用户说“已上传”“已申请”只说明用户已操作，AI有检查权限后仍要验证；未连通时标“用户已确认，未自动验证”。

### 2.3 每次授权卡必须说明

目标主机或容器、操作目的、完整命令或配置差异、影响范围、是否写入/下载/占用算力、敏感权限、授权有效范围，以及“授权执行 / 我来操作 / 取消”。不默认勾选，也不自动替用户同意。

表中“自动检查”均指已获得相应范围授权后；“回显”指真实工具结果，不能由语言模型编造。

| 7.3 | 展示和解释生成结果 | 直接整理真实结果 | 可选择修改提示词、再次生成 | 生成文本、原始JSON、验证结果；新增请求不能默默重发 |

## 4 按原文逐步展开

### 步骤1 环境准备

**原文依据**：第2.2节“环境准备”，NPU截图和Docker回显截图。

原文命令，在服务器主机执行：

```sh
npu-smi info
docker ps
```

**AI可以做**：获得只读授权后执行两条命令，解析设备是否可查询、Health字段和Docker查询状态，把两项检查分别回显。

**用户需要做**：选择实验主机并授权。主机连接和授权是产品补充前置，原文默认用户已具备服务器终端。如果驱动、固件或Docker未就绪，不把“环境检查授权”自动扩展成安装、升级或启动系统服务的权限。

**结果卡片建议**：

- NPU卡：设备编号、名称（若能获得）、Health、驱动工具版本（若回显提供），下方可展开完整输出。
- Docker卡：执行成功/失败、退出码、正在运行的容器数量、原始表格。
- 汇总：两项都通过才“环境检查通过”。若只通过一项，显示“1/2通过”，保留失败项及下一步。

**重要判断**：Docker只回显`CONTAINER ID / IMAGE / COMMAND / CREATED / STATUS / PORTS / NAMES`表头而没有数据行，表示查询成功但当前没有运行中的容器，不是报错。NPU查询成功也不等于固件和驱动的所有兼容性都已检查。

**异常分支**：命令不存在、Docker不可连接、权限不足、NPU Health异常，均显示真实错误并停止推进；提供重新检查、手动处理、查看原文安装指南。驱动/固件安装和可能的重启单独列为管理员处理，不纳入第一版自动执行。

### 步骤2 下载模型权重

**原文依据**：第2.2节“下载模型权重”，Hugging Face文件清单及上传服务器截图。

原文提供Qwen/Qwen2-7B仓库地址，并要求先下载至本地、再上传服务器任意目录；示例实际目录为`/home/lgy/Qwen2-7B/`。**原文没有提供下载命令或上传命令。**

**建议提供三个选项**：

1. “服务器已有权重”：选择服务器目录 → 授权检查 → 跳过下载和上传。
2. “本地已有权重”：选择本地目录 → 确认目标目录 → 授权上传 → 检查。
3. “还没有权重”：确认模型仓库、版本和落盘位置 → 授权下载 → 上传 → 检查。

服务器直接下载可以作为后续扩展，但与手册的本地下载后上传流程不同，需要明确标成替代方案，并确认目标服务器可联网；本稿不把它当作原文步骤。

**文件检查依据**：原文截图包含`config.json`、`generation_config.json`、`model-00001-of-00004.safetensors`至`model-00004-of-00004.safetensors`、`model.safetensors.index.json`、`tokenizer.json`、`tokenizer_config.json`、`merges.txt`、`vocab.json`等。具体必需文件集合要以选定仓库版本为准，不硬编码截图文件数量作为通用成功条件。

**需要用户确认**：下载位置、上传目标、已有文件冲突、网络/存储开销、是否改用不同模型。账号或访问凭据若确有需要，由用户在安全界面提供，不要求在聊天中粘贴。

**回显**：模型标识与版本、服务器目录、文件清单、下载/上传进度、缺失分片、校验依据。文件存在只能称“存在检查通过”；若未做可信清单/校验值比对，不显示“权重完整性验证成功”。不展示用户机器的无关目录。

### 步骤3 MindIE容器镜像获取

**原文依据**：第2.2节“MindIE容器镜像获取”，镜像选择、申请权限及下载弹窗截图。

原文实验镜像：

```text
swr.cn-south-1.myhuaweicloud.com/ascendhub/mindie:2.0.RC1-800I-A2-py311-openeuler24.03-lts
```

**AI可以做**：在授权后查询实际环境，提出匹配的镜像候选；已存在镜像时先核对，不强制重复拉取。用户完成仓库认证且同意拉取后，展示最终命令和实际拉取进度。

**用户需要做**：确认硬件型号、架构、镜像版本；选择“已有权限 / 去申请 / 使用本地镜像”；必要时登录仓库、申请权限、输入凭据。Agent可以引导打开相关页面，但不擅自提交个人信息或代替用户接受条款。

**原文截图中的拉取命令形式**：

```sh
docker pull <用户确认的完整镜像名称>
```

尖括号为本稿的参数占位，不是可直接运行的命令。自动化时必须渲染成已确认的实际镜像标识。登录用户名和密码不从手册截图复制。

**回显**：权限状态、等待审核（非失败）、认证状态、拉取进度、镜像ID/Tag/架构、实际大小和是否复用缓存。文档中的审核时间和镜像大小仅是当时描述，不能承诺当前一定如此。

**阻断条件**：无访问权限、认证失败、下载中断、存储不足、设备/架构不匹配。不能用另一种镜像悄悄替换以追求“完成”。

### 步骤4 启动容器

**原文依据**：第2.2节“启动容器”及参数详解。

原文的检查命令：

```sh
ll /dev/ | grep davinci
docker images
```

原文启动命令如下，**仅用于核对，不应一键照抄执行**：

```sh
docker run -it -d --net=host --shm-size=1g \
  --name qwentry6 --privileged=true \
  -w /home \
  --device=/dev/davinci4 \
  --device=/dev/davinci_manager \
  --device=/dev/hisi_hdc \
  --device=/dev/devmm_svm \
  -v /usr/local/Ascend/driver:/usr/local/Ascend/driver:ro \
  -v /usr/local/dcmi:/usr/local/dcmi:ro \
  -v /usr/local/bin/npu-smi:/usr/local/bin/npu-smi:ro \
  -v /usr/local/sbin/:/usr/local/sbin:ro \
  -v /home/lgy/Qwen2-7B/:/home/weights:ro \
  swr.cn-south-1.myhuaweicloud.com/ascendhub/mindie:2.0.RC1-800I-A2-py311-openeuler24.03-lts bash
```

**用户参数卡**：

| 参数 | 手册示例 | 产品应如何处理 |
|---|---|---|
| 容器名 | 命令为qwentry6，解释和后续命令为qwen | 用户确认一个名称，后续统一引用 |
| NPU设备 | /dev/davinci4 | 从实际设备列表选取，不把4固定给所有用户 |
| 主机权重目录 | /home/lgy/Qwen2-7B/ | 关联步骤2确认的服务器目录 |
| 容器权重目录 | /home/weights | 后续配置自动引用此值 |
| 权重挂载方式 | ro | 明确只读，不默默改为可写 |
| 镜像 | 步骤3的历史示例 | 关联用户选定并核对过的镜像 |
| 网络 | --net=host | 显示使用主机网络的影响并确认 |
| 容器权限 | --privileged=true | 明确高权限风险，单独确认；不能以“下一步”代替同意 |

**回显**：执行命令、实际容器ID、运行状态、容器名、选定镜像、设备及权重挂载路径。原文以容器ID回显作为启动成功提示；产品建议进一步核对运行状态，避免容器创建后立即退出仍显示完成。

**异常分支**：同名容器已存在时提供“查看现有容器 / 换名字 / 取消”，不自动删除或重建；设备或路径不存在时返回参数卡，不执行启动命令。

### 步骤5 模型推理配置

**原文依据**：第2.2节“模型推理”。

进入容器的原文命令：

```sh
docker exec -it qwen /bin/bash
```

这里的`qwen`必须替换为步骤4最终确认的容器名。对话卡始终显示“当前执行位置：主机 / 容器〈名称〉”。

容器内初始化的5条原文命令：

```sh
source /usr/local/Ascend/ascend-toolkit/set_env.sh
source /usr/local/Ascend/nnal/atb/set_env.sh
source /usr/local/Ascend/atb-models/set_env.sh
source /usr/local/Ascend/mindie/latest/mindie-llm/set_env.sh
source /usr/local/Ascend/mindie/latest/mindie-service/set_env.sh
```

**自动化约束建议**：这些初始化必须作用于后续启动服务使用的容器执行环境；不能每条命令各起一个独立会话后，误以为环境变量会自动保留。脚本没有文字输出不等于失败，必须记录执行结果，并检查必要环境是否可用。

配置文件原文位置：

```text
/usr/local/Ascend/mindie/latest/mindie-service/conf/config.json
```

建议先读取当前文件，展示以下字段的差异，确认后备份并只修改相关字段：

| 字段 | 原文修改后示例 | 用户确认内容 | 自动校验建议 |
|---|---|---|---|
| httpsEnabled | false | 本次是否接受实验中的非HTTPS配置 | 必须说明访问边界；非隔离环境不可静默关闭 |
| npuDeviceIds | [[0]] | 容器内实际可用设备及映射 | 不能直接拿主机设备4推导容器内编号0 |
| modelName | qwen2-7b | 本次部署的模型名称 | 与选定模型保持一致 |
| modelWeightPath | /home/weights/ | 关联已确认的容器挂载路径 | 路径存在且可读，所需文件可访问 |
| worldSize | 1 | 使用的推理卡数 | 与该版本配置要求、实际设备及选择数量核对 |
| trustRemoteCode | false | 默认保留false | 若需要改为true必须另行解释并授权，不自动放开 |

以下是把原文示例修为合法JSON后的**字段合并片段**，不是完整配置文件，不得覆盖原文件的其他字段：

```json
{
  "ServerConfig": {
    "httpsEnabled": false
  },
  "BackendConfig": {
    "npuDeviceIds": [[0]],
    "ModelDeployConfig": {
      "ModelConfig": [
        {
          "modelName": "qwen2-7b",
          "modelWeightPath": "/home/weights/",
          "worldSize": 1,
          "trustRemoteCode": false
        }
      ]
    }
  }
}
```

**回显**：5个初始化脚本的结果、当前容器上下文、文件备份位置、字段差异、JSON校验、路径与设备一致性检查。完成文案为“配置已应用并通过静态检查”，不能提前写“模型部署成功”。

**失败处理**：路径不可读、设备数量冲突、脚本缺失、JSON原文不合法时，先给修复建议和差异预览，未经授权不覆盖。若应用失败，保留原文件并解释失败点；回滚也要说明目标和影响。

### 步骤6 启动MindIE服务

**原文依据**：第2.2节“启动MindIE服务”。容器内原文命令：

```sh
cd /usr/local/Ascend/mindie/latest/mindie-service
nohup ./bin/mindieservice_daemon > output.log 2>&1 &
tail -f ./output.log
```

**执行前授权**：说明将占用选定NPU和内存、创建后台服务、写日志；核对预期端口和访问范围。原命令的`> output.log`会覆盖同名日志，已有日志时必须提供保留或改用新日志文件的选择，不能默认覆盖。

**运行中反馈**：区分“命令已提交”“服务启动中”“启动日志通过”“服务可用”。原文截图成功标记为：

```text
Daemon start success!
```

该标记可以作为原文提供的一个判断依据，但产品建议结合当前进程、端口及可用检查，避免读取旧日志导致误判。检查方法和超时阈值在实现前与执行端确认，未提供的健康检查接口不能假设存在。

**回显**：后台进程信息、日志文件、开始时间、最新日志、成功标记或真实错误、超时状态。脱敏后可展开原始日志。

**退出观察**：原文要求Ctrl+C退出`tail`。界面建议显示“停止日志观察”，明确服务继续运行。停止服务是不同操作，需要另行授权；不得把Ctrl+C解释成服务停止。

### 步骤7 推理交互

**原文依据**：第2.2节“推理交互”。原文命令：

```sh
curl -H "Accept: application/json" -H "Content-type: application/json" -X POST -d \
'{
"prompt": "介绍下Qwen2-7B",
"max_tokens":500
}' \
http://127.0.0.1:1025/generate
```

**用户选择**：“使用手册示例 / 输入自己的问题”，可调整`max_tokens`。提交前显示最终提示词、参数、请求地址及实际执行环境。`127.0.0.1`指执行请求所在的环境，不应未经说明改成用户浏览器本机。

**授权范围**：发送这一条请求。修改提示词、增加生成量或自动重试不能沿用模糊授权无限执行；可在同一轮授权中明确限定重试次数，否则失败后先询问。

**结果卡片**：

- 概览：请求成功/失败、HTTP状态码、执行耗时；没有真实计量时不编造Token数。
- 正文：优先展示响应中的`text`，保留原始JSON的展开入口。
- 对照：用户问题、模型名称、请求参数，方便理解此次结果对应哪次执行。
- 后续：修改问题、再次生成、查看终端、保存笔记。

**成功条件建议**：请求传输成功、HTTP结果符合预期、响应可解析且包含预期文本字段。命令退出码为0不必然代表业务成功；HTTP错误或空结果不能显示实验已完成。

原文生成文本截图只作为返回结构示意。其中对模型架构的自然语言描述可能不准确，不应复制为标准知识结论或正确答案。服务返回成功和生成内容事实正确是两个维度。

## 6 结果卡片和顶部状态规范

### 6.1 统一结果卡片字段

| 区块 | 字段 | 显示规则 |
|---|---|---|
| 标题 | 步骤号、动作名、状态 | 如“1.2 NPU检查 已通过” |
| 执行上下文 | 主机/容器、目录、时间 | 敏感主机信息按产品脱敏规则显示 |
| 操作记录 | 实际命令或配置差异、授权关联 | 能追溯本次究竟做了什么 |
| 原始证据 | stdout、stderr、退出码、HTTP状态等 | 默认摘要，可展开；密码/Token必须过滤 |
| AI解释 | 结果含义、是否达到当前条件 | 与原始证据区分；不能凭文字解释覆盖错误 |
| 下一步 | 继续、修改参数、重试、手动处理 | 失败时只阻断依赖该动作的后续任务 |
| 来源标记 | 真实执行 / 用户提供 / 手册示例 | 三者始终可区分 |

建议保留执行记录ID、授权ID、参数版本和文件差异版本，避免用户改了命令后结果仍错误关联旧参数。此为交互和证据要求，不是本轮接口设计。

### 6.2 顶部7步的状态

`未开始 → 等待选择或授权 → 执行中 → 验证中 → 已完成`

另有：等待外部审核、失败待处理、已暂停、已取消。状态必须有文字，不只靠颜色。

- 点击顶部步骤用于定位对话和查看结果，不意味着重新执行。
- 点击“下一步”只推进导航，不代表自动同意下一阶段授权。
- 用户查看过步骤不算完成；必须达到该步的证据条件。
- 改变上游权重路径、设备或镜像后，下游结果标“需重新验证”，不能保留错误的绿色完成状态。
- 关闭AI学伴不应默默终止后台服务；正在进行的任务状态需要能再次查看。
- 用户暂停后不发起新命令；已发出的任务是否可以中止，执行端须返回真实状态，不以“关闭气泡”假装停止成功。

## 8 建议第一版范围与待你确认的决定

### 8.1 第一版建议

保持现有学习框架，在实践视角的AI学伴内承载7步导航、选择卡、授权卡、真实用户回复气泡、命令记录和结果卡。不新增另一套独立产品框架。

先做“只读环境检查 → 已有权重/镜像复用 → 容器参数确认 → 配置差异确认 → 启动服务 → 推理请求”的闭环。下载上传、账号申请可按同一模型补充，但不要为了演示完整流程把外部审核伪造成瞬间成功。

不把驱动/固件安装升级、主机重启、自动放开远程代码权限、删除旧容器、清理旧权重和关闭安全机制纳入默认自动化。需要时另开明确授权流程。

### 8.2 优先确认的6项

1. **顶部数量与命名**：保留7步，第5步改叫“模型推理配置”，是否同意？
2. **授权粒度**：第一步两条只读命令合并授权，其余写入/下载/启动动作分阶段确认，是否同意？
3. **授权选项**：统一“授权执行 / 我来操作 / 取消”；点击授权后右侧生成明确范围的用户回复气泡，是否同意？
4. **真实还是演示**：下一轮先做明确标注的交互演示，还是已有可连接实验执行端？没有执行端时，所有回显必须标“演示数据”。
5. **步骤推进**：结果自动验证通过后显示“继续下一步”，由用户继续；不自动连跑全部7步，是否同意？
6. **失败修复**：沿用现有“错误代码与正确示例对照”，先展示差异、用户确认再应用；应用后标“待重新验证”，是否同意？

### 8.3 评审验收点

- 7个主步骤与25个子任务能一一对应，原文和产品新增逻辑可区分。
- 每个真实执行动作前有符合范围的授权，不生成虚假的用户同意。
- 用户能看懂命令在哪执行、会改什么、结果意味着什么。
- 空Docker表、无脚本输出、等待审核都不会被误报为失败。
- 容器创建、配置应用、服务启动、请求成功分别验证。
- 失败有原始证据和恢复路径，不自动覆盖、删文件或扩大权限。
- 尚未执行或未连接时不说“已完成”；演示结果始终带来源标记。
